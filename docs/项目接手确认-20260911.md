### 5.1 `core/agent.py` 有 243 处乱码，且包含面向客户的兜底话术

文件是合法 UTF-8，但内容是 GBK 字节被二次编码后的残留。受影响的**不只是注释**：

| 触发场景 | 客户看到的 |
|---|---|
| 限流命中 | 乱码 |
| 黑名单命中 | 乱码 |
| 提示词注入拦截 | 乱码 |
| 主备模型全部调用失败 | 乱码 |
| `sales_prompt.txt` 缺失时的兜底人设 | 整段乱码 |

平时走 `config/sales_prompt.txt` 时正常，所以自测很难发现；**一旦限流或模型故障，客户会收到乱码**。

### 5.2 `core/tasks.py:179` 的重试分支永远不会命中

```python
if not result.get("ok") and result.get("error") == "?????????":
    raise self.retry(countdown=5)
```

中文被编码丢成了问号，这个等值判断永远为假 → Celery 渠道回复失败后不会重试。同时 `core/tasks.py`、`connectors/wecom.py` 还有共 6 行 `????` 形式的编码丢失。

### 5.3 桥接里有三个"看着有、其实没接线"的配置项

`wechat_bridge/config.py` 解析了、配置文件里也写了，但 `run.py` 从头到尾没使用：

### 5.4 非 UTF-8 编码文件（3 个）

`check_brackets.js`、`start_vision_agent.bat`（GBK）、`static/solda.js.gbk.bak`（本身就是备份）。前两个在中文 Windows 能跑，但拿到 UTF-8 环境（如 Linux 服务器）执行 `start_vision_agent.bat` 可能因中文变乱码而失败。

### 10.6 排障记录：前端不显示「已登录」（2026-09-11 14:15）

**现象**：微信客户端已登录，但中台「客户接待链路」页面的登录状态不显示「当前已登录」。

**根因：不是前端故障，也不是登录检测故障，而是桥接没有运行。**

前端**自己不检测微信登录**。`static/console.html:3597` 的登录徽标取的是 `inst.wechat_login_detected`，数据来自 `GET /api/v1/personal-wechat/status`；而云端 `personal_wechat_bridge_instances` 表**只由本机桥接的心跳写入**（`POST /api/v1/personal-wechat/bridge/heartbeat`）。桥接没跑 → 没有心跳 → 该表没有新数据 → 页面只能显示「离线」+「当前未检测到登录」。

同时 `online` 的判定是「`last_seen` 在 90 秒内」（`core/personal_wechat.py` 的 `status()`），所以离线时该字段必然为 false。

**实测：本机登录检测本身完全正常。** 直接调用链路得出的结果：

### 10.8 ⚠️ 新发现问题：云端时间戳是 UTC，比本地慢 8 小时

验证时看到 `last_seen: 2026-09-11 06:20` 而本地时间是 14:20，相差正好 8 小时 —— **容器内 `datetime.now()` 取的是 UTC**。

- 功能上**不受影响**：`online` 判定（`core/personal_wechat.py` 的 `status()`）两端都用服务端时间，自洽；任务的 `expires_at`、`lease_expires_at` 同理。
- 但**展示上会混乱**：`last_seen` 是 UTC，而桥接上报的 `last_message_at` / `last_reply_at` 是本地北京时间。同一个页面上混着两个时区。
- 建议：在容器里设 `TZ=Asia/Shanghai`（并在 `docker-compose.yml` 的 api / worker / beat 三个服务上加 `TZ` 环境变量），或统一改成 UTC 存储 + 前端转换。
