## 2. 产品背景与现状问题

### 2.1 产品已经做出来的核心能力

- AI 销售客服：DeepSeek + RAG + 客户画像 + 销售阶段识别。
- CRM 数据层：客户、线索、商机、订单、回款、跟进等模型与接口。
- 渠道接入：企业微信自建应用、微信客服、公众号、网页客服、个人微信机器人。
- 消息调度：已具备消息幂等、Redis 用户锁、定时任务、异步回复雏形。
- 中台控制台：网页版与桌面版入口。
- 视觉执行器：仿识流 AI 的桌面自动化通道。
- 商业化雏形：租户、许可证、账户、API Key、审计等基础能力。
- 部署形态：PostgreSQL + Redis + Celery + Docker Compose。

### 2.2 当前“乱”的来源

项目不是没有功能，而是缺少一个统一的产品结构，导致出现以下问题：

1. 模块边界不统一。同一类能力被拆到多个页面、多个 API、多份前端文件里。
2. 渠道逻辑不统一。企业微信、微信客服、公众号、个人微信各有一套回调与回复链路，重复回复和上下文不一致的根因在这里。
3. 桌面端存在两套实现。`desktop_app`（pywebview）与 `desktop-client`（Electron）同时存在，产物和入口互相混淆。
4. 前端存在多份复制。`static/console.html`、`desktop_console.html`、`renderer/index.html` 等出现手工同步，容易改一漏三。
5. 部署依赖补丁包。大量 `*-20260828.zip`、`docker cp` 方式部署，缺少“单一构建产物、可重复部署”的基线。
6. 模块页面存在空数据、英文残留、JSON/代码裸露等情况，不能作为对外商用界面交付。
7. 文档与真实能力不同步。旧文档描述过多规划态能力，用户无法判断哪些已经可用。

### 2.3 整改总目标

从“验证型 Demo 堆叠”整改为“可售卖、可交付、可测试、可审计”的企业级产品：

- 一个产品入口：桌面客户端与网页端共用同一中台能力。
- 一套会话协议：所有渠道进入同一条消息处理链路。
- 一套数据底座：客户身份统一、租户隔离完整、审计可查。
- 一套前端工程：不再维护多份复制页面。
- 一套部署产物：镜像构建与全量同步脚本取代零散 ZIP 补丁。
- 一套文档体系：PRD、技术设计、部署手册、验收报告各自唯一。

## 3. 产品定位

产品名暂定：销售智能体商业版（内部代号 WorkBuddy Agent）。

一句话定位：面向中小企业的私域销售与客服自动化中台，用 AI 承接客户咨询、沉淀客户资产、管理销售过程，并通过桌面客户端提供带风控的微信/企业微信自动触达能力。

核心价值主张：

1. 客户来消息，AI 先接住，真人随时可接管。
2. 客户资产不散落在个人微信，统一沉淀到企业自己的中台。
3. 自动回复不等于裸奔，所有通道有去重、限流、风控、审计和人工兜底。
4. 每个企业登录后只看到自己的数据，可作为独立 SaaS 交付给其他客户。

非目标（V1 明确不做）：

- 不做一个大而全的 ERP。
- 不做自有支付牌照、呼叫中心硬件、短信服务商。
- 不承诺通过非官方个人微信通道实现 100% 零风险。
- 不做与客户生命周期无关的伪功能页面。

## 4. 用户与场景

### 4.1 用户角色

| 角色 | 说明 | 核心诉求 |
|---|---|---|
| 企业主 / 经营者 | 购买并使用系统的人 | 客户消息有人自动接，转化过程可看，数据不流失 |
| 销售 / 客服 | 日常接待客户的人 | AI 辅助回复，自己能接管、转派、跟进 |
| 实施管理员 | 配置渠道、知识库、权限的人 | 配置简单、状态可见、出问题可查 |
| 平台运营 | 运营这套 SaaS 的人 | 租户、套餐、用量、许可证、审计全部可控 |
| 最终客户 | 通过各渠道咨询企业的用户 | 得到快速、专业、不重复打扰的回复 |

### 4.2 关键用户故事

1. 企业主：客户通过企业微信或个人微信发来咨询，AI 能基于我的产品资料回答；客户要求人工时，消息转到指定同事，AI 不再抢答。
2. 客服：同一客户连续发来多条消息时，系统按顺序生成回复，不会同时冒出多个机器人重复回复。
3. 群运营：我只想机器人在指定群内工作，群外私聊和无关群一概不理；新成员进群时自动发欢迎语。
4. 实施管理员：我配置知识库、商品、渠道后，能通过中台看到每一路渠道是否在线、发了什么、失败原因是什么。
5. 企业客户：我下载桌面客户端、输入公司账号登录，只能看到本公司的客户与线索，看不到其他企业数据。
6. 平台运营：我能给客户开试用、升级套餐、设置席位与视觉执行器权限，并能查询每一次自动发送的审计记录。

## 5. 总体架构

### 5.1 分层结构

```text
接入层
  Web 中台 / 桌面客户端 / 官网下载站
  企业微信自建应用 / 微信客服 / 公众号 / 网页客服 / 个人微信机器人 / 视觉执行器

控制层
  账号登录 / 租户隔离 / 权限 RBAC / API Key / IP 白名单
  许可证 / 套餐 / 用量 / 审计 / 告警

业务层
  消息中枢：事件归一化 -> 去重 -> 路由 -> 会话 -> AI 回复 -> 渠道发送
  销售 Agent：LLM + RAG + 客户画像 + 销售阶段 + 话术策略
  CRM 业务：客户 / 线索 / 商机 / 订单 / 跟进 / 质检 / 工单
  增长业务：营销活动 / 自动跟进 / 培育计划
  数据业务：经营看板 / BI / 报表 / 指标中心
  视觉执行器：实例管理 / 任务调度 / 风控 / 人工接管 / 审计

数据层
  PostgreSQL：租户业务数据
  Redis：会话 / 队列 / 分布式锁 / 限流 / 幂等
  对象存储或本地磁盘：知识库文件 / 语音 / 图片 / 导出文件
```

### 5.2 统一消息处理链路

这是全产品最重要的技术约定。所有渠道必须进入同一条链路：

```text
渠道消息
  -> 渠道适配器归一化为统一事件
  -> 幂等检查（渠道 msg_id 或事件指纹）
  -> 识别用户身份（渠道用户 ID -> 客户 / 线索）
  -> 创建或复用统一会话
  -> 路由策略判断（自动 / 仅 @ / 人工接管 / 关闭）
  -> 同用户串行锁或固定路由，保证上下文一致
  -> 销售 Agent 生成回复
  -> 合规与风控检查
  -> 分条发送、自然延迟、渠道适配器发送
  -> 会话状态与 CRM 副作用更新
  -> 审计日志记录
```

禁止各渠道各自调用 LLM 后再自行发送。渠道只负责“收到事件”和“发送结果”，不允许承担去重、上下文、客户建档等业务规则。

原项目中的“伪模块”应先收敛到以下模块，避免再新增并列的“同名能力页面”。

```text

  经营首页 / 待办与告警 / 数据看板

客户经营
  客户档案 / 客户 360 / 线索管理 / 公海池 / 商机

  企业微信 / 微信客服 / 公众号 / 个人微信群聊 / 网页客服 / 视觉执行器

营销增长
  自动跟进 / 营销活动 / 培育计划 / 内容与话术

  文档管理 / 向量索引 / 版本 / 反馈回灌

  登录 / 本租户中台 / 视觉执行器开关 / 自动更新（后阶段）
```

### 6.2 模块最小准入条件

任何模块只有同时满足以下条件才算“已交付”：

1. 有统一菜单入口和中文页面标题。
2. 页面不是空白、不是 JSON、不是代码报错。
3. 数据有明确的列表、筛选、分页、详情。
4. 操作有权限校验与审计。
5. 没有数据时给出业务化空状态，而不是裸表或报错。
6. 有后端测试与验收用例。
7. 与租户隔离规则一致。

## 7. 功能需求

### 7.1 渠道接入与消息中枢（P0）

#### FR-101 渠道统一状态

| 编号 | 需求 |
|---|---|
| FR-101 | 中台渠道页展示每个渠道的连接状态、回调地址、最近心跳、最近错误 |
| FR-102 | 支持企业微信、微信客服、公众号、网页客服、个人微信机器人分别启停 |
| FR-103 | 渠道配置变更必须记录审计日志 |
| FR-104 | 渠道接入参数由后台管理，不允许出现在前端代码中 |

验收标准：
- 任一渠道断线后，状态页在 1 分钟内可见异常。
- 重新配置密钥或回调后无需重启整站，渠道可重新上线。

#### FR-110 个人微信群聊机器人

个人微信机器人独立作为“渠道接入 -> 个人微信群聊”模块管理，不与其他渠道耦合。

| 编号 | 需求 |
|---|---|
| FR-110 | 机器人支持配置目标群白名单，只处理指定群 |
| FR-111 | 群内回复模式支持“仅 @ 机器人”“全部文本”“关闭自动回复” |
| FR-112 | 支持 `personal_auto_reply` 开关，私聊默认不回复 |
| FR-113 | 新成员进群自动发送欢迎语，欢迎语内容可在配置中修改 |
| FR-114 | 欢迎语只发一次，重复进群事件在短时间内自动去重 |
| FR-115 | 语音、图片消息可转 AI 处理 |
| FR-116 | 长回复自动分条，单条长度与分条间隔可配置 |
| FR-117 | 同一会话上下文不串号，每个用户使用独立会话 ID |
| FR-118 | 机器人自身账号发起的消息不触发回复 |
| FR-119 | 非目标群消息只记录摘要，不调用 AI、不回复 |
| FR-120 | 支持目标群名称与显示名完全一致时匹配；支持从机器人侧列出当前群名辅助排错 |

验收标准：
- 配置目标群 `workbuddy-降本增效-实操群` 后，其他 13 个群的消息不会触发 AI。
- 同一用户同时发送 5 条消息时，只按顺序产生回复，不出现重复 AI 回复。
- 新成员进群时发送一次既定欢迎语；60 秒内重复收到同一入群事件不再发送。

#### FR-130 企业微信与微信客服

| 编号 | 需求 |
|---|---|
| FR-130 | 支持企业微信自建应用回调 `/wecom` 与微信客服回调 |
| FR-131 | 回调参数、Token、EncodingAESKey 全部从服务端配置读取 |
| FR-132 | 客户要求人工时自动转人工并通知归属人 |
| FR-133 | 转人工后 AI 停止自动回复，人工处理后可以恢复自动回复 |
| FR-134 | 微信客服消息与普通企业微信消息都进入统一消息中枢 |
| FR-135 | 已接入的真实账号、客服账号可在中台管理中查看 |

#### FR-140 公众号与网页客服

| 编号 | 需求 |
|---|---|
| FR-140 | 公众号关注、扫码、文本消息按统一消息模型入库 |
| FR-141 | 公众号带参二维码写入渠道来源 |

### 7.2 智能客服与销售 Agent（P0）

#### FR-201 对话能力

| 编号 | 需求 |
|---|---|
| FR-201 | 根据产品资料、价格、政策、课程大纲、案例库回答客户 |
| FR-202 | 使用 RAG 检索知识库并展示引用来源 |
| FR-203 | 自动识别客户姓名、电话、身份、目标、预算、课程兴趣 |
| FR-204 | 自动判断销售阶段：陌生 / 了解 / 意向明确 / 高意向 / 成交 |

| FR-207 | 支持按租户配置商品库与话术，不在代码里写死“产品名称” |

#### FR-220 回复防重复与上下文一致

| 编号 | 需求 |
|---|---|
| FR-220 | 所有渠道按 msg_id 或内容指纹做幂等 |
| FR-221 | 同一渠道同一用户同时到达的消息使用同用户锁或固定路由串行处理 |
| FR-222 | 每个用户会话使用稳定 session_id，Redis 会话与数据库会话保持一致 |
| FR-223 | 收到重复推送时不重复生成 LLM 回复、不重复发送 |
| FR-224 | 单条消息成功发送后记录发送状态，重试不得导致二次发送 |
| FR-225 | 同一用户的历史上下文在一个执行单元内读取，避免跨 worker 乱序 |

验收标准：
- 对同一用户并发投递相同内容 20 次，最终只发送一次回复。
- 用户连续发送“价格”“怎么报名”，上下文能理解是在问同一课程，不重复自我介绍。

#### FR-230 回复风格控制

| 编号 | 需求 |
|---|---|
| FR-230 | 自动回复前保留自然思考/输入间隔 |
| FR-231 | 长回复按语义拆分，URL 不截断 |
| FR-232 | 支持语音转文字与图片识别（按租户能力开启） |
| FR-233 | 回复可配置禁止承诺、强逼单、过度推销等合规规则 |
| FR-234 | 回复超时、LLM 报错时返回兜底文案或转人工，不静默失败 |

## 8. 关键业务流程

### 8.1 新客户进目标群

```text
用户扫码进群
-> 机器人收到 room-join
-> 校验是否目标群
-> 校验 welcome_on_join
-> 幂等去重
-> 群内发送欢迎语
-> 写审计日志
```

### 8.2 客户在渠道咨询

```text
客户发消息
-> 渠道回调
-> 统一消息中枢去重
-> 匹配客户身份
-> 路由策略判断
-> 同用户串行处理
-> AI + RAG + 画像生成回复
-> 合规检查
-> 分条发送
-> 记录会话与审计
-> 如触发人工则转交
```

### 8.3 视觉执行器主动触达

```text
中台创建触达任务
-> 服务端校验授权与限额
-> 下发到对应桌面实例
-> 桌面端打开联系人窗口
-> 截屏 -> 视觉识别 -> 确认目标
-> 模拟输入并发送
-> 上报发送结果
-> 中台审计
```

## 9. 数据模型（核心）

| 领域 | 主要实体 |
|---|---|
| 平台与系统管理 | tenant、account、member、role、permission |
| 渠道 | channel_account、channel_connection、bot_instance、target_room |
| 会话 | conversation、message、message_dedup、session_state |
| 客户 | customer、lead、contact_identity、follow_up、portrait |
| 交易 | opportunity、product、order、quote、contract、payment |
| 内容 | knowledge_doc、knowledge_chunk、content_asset |
| 服务 | handover、ticket、quality_record、satisfaction |
| 执行 | vision_instance、vision_task、vision_audit |
| 商业化 | license、plan、usage_record、billing |
| 系统 | audit_log、notification、alert_rule |

数据原则：

- 所有业务实体表包含 `tenant_id`，索引必须包含租户维度。
- Redis Key 使用 `tenant:{id}:` 前缀。
- 消息幂等按“租户 + 渠道 + msg_id / 指纹”唯一。
- 用户身份以“统一身份 ID”为事实，渠道 ID 只是别名。
- 删除业务数据使用软删除或审计回收，禁止直接物理删除后再无法追溯。

## 10. 非功能需求

### 10.1 性能与并发

- 普通文本回复首字延迟控制在可接受范围内，默认不因为渠道回调而阻塞。
- API 高峰期允许排队，但要快速返回“已接收”而非超时。
- 单用户消息必须串行，系统吞吐提升不能破坏上下文一致性。
- 个人微信通道遵守平台限制，默认按真人节奏回复。

### 10.2 稳定性与可运维

- API、Worker、Beat 分离，长任务不进 HTTP 请求。
- 所有关键路径提供健康检查、心跳、告警。
- 数据库每日备份，配置与代码回滚流程可执行。
- 部署用镜像/Compose 或全量同步脚本，不再要求手工 `docker cp` 单个文件。
- 关键文件编码统一 UTF-8，避免乱码。

### 10.3 安全合规

- 全站 HTTPS，回调签名校验。
- API Key 和 Token 不得写入前端、日志、聊天记录。
- 导出文件带租户标识与操作人信息。
- 个人微信/企业微信视觉通道必须说明平台风险并提供熔断。
- 审计日志至少覆盖：登录、渠道配置、自动发送、人工接管、导出、删除。

### 10.4 渠道风险分级

| 通道 | 是否官方 | 建议定位 |
|---|---|---|
| 公众号 / 企业微信自建应用 / 微信客服 | 官方 API | 合规主通道 |
| 网页客服 | 自有页面 | 官网引流 |
| 个人微信机器人 / 视觉执行器 | 非官方 / 半官方 | 企业明确授权后作为增值能力，默认关闭 |

## 13. 验收口径

每个 P0 模块使用以下四类验证：

1. 自动化验证：路由可调用、参数校验、关键断言通过。
2. 数据验证：数据库中真实字段存在、租户过滤正确、无乱码。
3. 界面验证：页面无空屏、无代码裸露、操作后数据可回读。
4. 业务验证：按真实角色完成一次端到端业务，如“客户进群 -> AI 回答 -> 转人工 -> 跟进”。

重点回归用例：

| 场景 | 预期 |
|---|---|
| 同用户并发相同消息 | 只回复一次 |
| 同用户连续不同问题 | 上下文连贯，不串客户 |
| 非目标群消息 | 不回复、不建档、不调用 AI |
| 新成员进目标群 | 发一次欢迎语 |
| 客户要求人工 | 停止自动回复并通知归属人 |
| 租户 A 查询客户 | 看不到租户 B 数据 |
| 视觉执行器未授权 | 不可发送，只有状态与授权入口 |
| 前端任意模块空数据 | 显示中文空状态，不显示 JSON |
| API 缺参数/权限不足 | 返回统一错误，不泄露堆栈 |

## 14. 上线判断标准

满足以下条件才允许作为对外版本发布：

1. 所有 P0 模块通过验收脚本。

5. 审计、备份、恢复流程验证通过。
6. 界面无乱码、无英文残留、无空白模块、无代码暴露。
