# 六项能力商用化落地实施方案

> 日期：2026-09-15  
> 范围：多租户隔离、权限体系、RAG 知识库、部署升级、测试体系、合规隐私  
> 原则：先保证数据安全和租户边界，再提升 AI 质量，最后完善发布和运维。

---

## 一、实施前置决策

以下决策会直接影响架构。正式动工前需要确认：

| 决策项 | 建议方案 | 影响 |
|---|---|---|
| 产品形态 | 支持多租户 SaaS，同时保留私有化部署 | 决定数据库、权限和知识库改造范围 |
| 向量库 | 使用 PostgreSQL + pgvector | 复用现有 PostgreSQL，运维成本最低 |
| 个人微信通道 | 继续保留，但定义为受控渠道，不作为唯一正式通道 | 决定风控、合规和测试策略 |
| 发布窗口 | 先允许 10 到 30 分钟维护窗口 | 降低第一期蓝绿部署复杂度 |
| 灾备目标 | 建议 RPO 不超过 24 小时，RTO 不超过 4 小时 | 决定备份频率和恢复演练 |
| 数据留存 | 聊天内容默认 180 天，审计日志 180 天，删除申请 15 天内完成 | 决定清理任务和合规流程 |
| 超管权限 | 只允许显式配置的超管凭据跨租户 | 防止默认越权 |
| API Key 管理 | Key 仅保存哈希，不明文存库，支持吊销和轮换 | 决定认证表和安全流程 |

## 二、多租户隔离

### 2.1 目标

任何租户只能访问自己的数据。即使猜到其他租户的客户编号、订单编号、会话编号或知识文档编号，也不能读取、修改或导出。

### 2.2 当前问题

- 客户、聊天记录、标签、通知、支付、售后、商机等核心表没有统一 `tenant_id`。
- 客户列表接口拿到了租户号，但仍然返回全部客户。
- 知识库和向量索引没有租户归属。
- Redis 去重键、限流键和缓存键没有统一租户前缀。
- PostgreSQL 唯一约束仍是全局唯一，同一租户下也不能出现相同会话编号。

### 2.3 数据改造

第一优先级表：

- `customers`
- `stage_log`
- `customer_chat_log`
- `customer_chat_archive`
- `notifications`
- `message_dedup`
- `behavior_events`
- `followup_tasks`
- `orders`
- `payments`
- `after_sales`
- `quality_reports`
- `knowledge_versions`
- `handover_requests`
- `opportunities`
- `quotes`
- `quote_lines`
- `contracts`
- `shipments`
- `invoices`
- `payment_plans`
- `receivables`
- `business_profiles`
- `stakeholders`
- `customer_tags`
- `risk_events`
- `sop_templates`
- `sop_executions`
- `tickets`
- `visits`
- `campaigns`
- `nurture_campaigns`
- `repurchase_plans`
- `custom_fields`
- `custom_field_values`
- `roles`
- `ai_reports`

### 2.4 数据库迁移顺序

1. 新增可空 `tenant_id`，不能立即设为非空。
2. 从父表或已有会话、客户、线索、订单关系回填租户。
3. 无法确定归属的历史数据统一回填到 `DEFAULT_TENANT_ID`，并生成异常报告。
4. 回填完成后增加索引，例如 `(tenant_id, id)`、`(tenant_id, session_id)`。
5. 将全局唯一约束改成租户内唯一，例如 `(tenant_id, session_id)`。
6. 数据库启动时校验是否存在 `tenant_id IS NULL`。
7. 校验通过后再执行 `NOT NULL`。
8. 旧版本代码继续保持兼容，不能同一发布同时切换全部读写。

### 2.5 应用层改造

- 所有业务查询必须经过统一仓储层，不允许接口直接写无租户条件的 SQL。
- `tenant_id` 只能从登录令牌或服务凭据获取，禁止由客户端请求体自报。
- 所有 Redis Key 增加租户前缀，例如 `tenant:{id}:reply:lock:{session}`。
- 所有对象存储路径增加租户目录，例如 `tenants/{tenant_id}/knowledge/...`。
- 超管跨租户读取必须显式调用专用接口，并写高等级审计。
- 后台任务必须携带 `tenant_id`，禁止从全局数据中猜租户。
- 客户、线索、订单等公开编号改为租户内唯一，并在界面显示时拼接受控前缀。

### 2.6 验收标准

- 双租户测试中存在相同客户编号、订单编号和知识文件名时，双方互不可见。
- 客户列表、客户详情、订单详情、导出、删除接口全部通过越权测试。
- 所有新增业务表 `tenant_id` 完整率达到 100%。
- Redis、对象存储和本地桥接队列不存在无租户归属的数据。
- 超管跨租户操作全部有审计记录。

### 2.7 回滚

- 第一阶段只加字段和索引，不影响旧版本读写。
- 第二期切换仓储层时使用功能开关，可即时切回旧查询实现。
- 数据库结构回滚只删除新增索引和字段，不删除原业务数据。

## 三、权限体系

### 3.1 目标

建立后端强制执行的 RBAC、数据范围和资源动作权限。前端隐藏按钮只能改善体验，不能作为安全边界。

### 3.2 角色设计

| 角色 | 数据范围 | 典型权限 |
|---|---|---|
| 平台超管 | 全部租户 | 租户管理、许可证、平台配置 |
| 企业所有者 | 本租户全部数据 | 账号、计费、权限、全部业务 |
| 企业管理员 | 本租户全部数据 | 配置、知识库、渠道、审计 |
| 销售主管 | 本团队或全部客户 | 分配、跟进、查看团队数据 |
| 销售 | 本人负责客户 | 客户、线索、跟进、订单查看 |
| 客服 | 分配会话和工单 | 会话、工单、转人工、回访 |
| 财务 | 财务相关数据 | 订单、回款、发票、应收 |
| 只读审计 | 本租户只读 | 审计、报表、导出审批 |
| 服务账号 | 限定接口和资源 | 桥接、定时任务、系统集成 |

### 3.3 权限模型

权限统一表示为：

`resource:action:scope`

示例：

- `customer:read:own`
- `customer:update:team`
- `knowledge:approve:all`
- `order:read:all`
- `audit:read:all`

### 3.4 实施步骤

1. 建立 `roles`、`permissions`、`role_permissions` 和 `user_roles`。
2. 每个角色权限必须带租户 ID，不能复制全局角色后再共享修改。
3. Token 登录从数据库加载角色和权限，不完全依赖前端保存的用户对象。
4. 服务账号单独建表，API Key 保存哈希、租户、权限、过期时间和吊销状态。
5. 后端建立统一依赖，例如 `require_permission("customer:read")`。
6. 查询层增加数据范围条件，区分本人、团队、本租户和全部租户。
7. 前端根据权限渲染菜单和按钮，收到 403 后统一提示，不显示技术错误。
8. 高风险管理操作增加二次确认和审计，包括导出、删除、授权、权限调整和密钥轮换。

### 3.5 API Key 规则

- API Key 不再默认视为管理员。
- 如需管理员权限，必须绑定明确角色，不能用“已登录”代替。
- Key 只显示一次，数据库只保存哈希。
- 每个 Key 记录租户、用途、创建人、最后使用时间、过期时间和状态。
- 支持一键吊销和轮换，轮换期间允许旧 Key 短暂并行。

### 3.6 验收标准

- 普通销售直接请求管理员接口必须返回 403。
- 销售无法通过修改客户编号访问别的销售或别的租户数据。
- 前端手动输入 URL 也无法进入无权限页面。
- 权限调整、导出、删除、Key 轮换全部有审计。
- 管理员 Key 与普通业务 Key 的权限测试通过。

## 四、RAG 知识库

### 4.1 目标

知识文档、切片、向量、索引版本和检索结果全部按租户隔离，支持版本审批、可回滚、可评测，并能处理真实商用知识规模。

### 4.2 技术选型

第一期采用 PostgreSQL + pgvector，原因是：

- 复用现有 PostgreSQL，不增加独立向量数据库。
- 可以使用数据库事务、租户条件和权限过滤。
- 迁移和备份沿用现有数据库方案。
- 后续数据量增长后再评估 Milvus 或 OpenSearch。

### 4.3 新数据结构

- `knowledge_documents`：文件元数据、租户、来源、版本、审批状态。
- `knowledge_chunks`：切片内容、文档 ID、租户、序号、标签。
- `knowledge_embeddings`：向量、模型、维度、索引版本。
- `knowledge_index_versions`：构建状态、开始时间、完成时间、当前发布版本。

### 4.4 导入和发布流程

1. 上传文件。
2. 校验格式、大小、病毒和编码。
3. 解析文本和元数据。
4. 按租户和文档类型切片。
5. 生成向量并写入新索引版本。
6. 运行质量检查，例如空切片、乱码、重复和低信息量检测。
7. 管理员审批。
8. 原子切换当前版本。
9. 旧版本保留指定天数，支持回滚。

### 4.5 检索流程

1. 先按租户、审批状态、文档范围、时间和权限过滤。
2. 使用全文检索和向量检索做混合召回。
3. 使用重排模型或规则重排。
4. 只把通过阈值的片段交给模型。
5. 输出引用来源、文档版本和切片位置。
6. 没有可靠知识时返回“信息不足”或转人工，不能允许模型自由编造。

### 4.6 评测指标

- 召回率 Recall@K。
- 引用正确率。
- 有依据回答率。
- 无依据回答率和幻觉率。
- 无答案识别准确率。
- 回答延迟 P95。
- 单次检索和生成成本。

### 4.7 验收标准

- 任意检索请求只返回当前租户数据。
- 待审批和已拒绝文档不能进入检索。
- 历史版本可以回滚。
- 每条有知识依据的回复都能定位到文档和切片。
- 知识库不可用时降级到安全兜底，不直接调用无依据模型回答。

## 五、部署升级

### 5.1 目标

从手工上传文件升级为可重复、可验证、可回滚的标准化发布流程。

### 5.2 代码和版本管理

- 建立 Git 仓库，禁止直接把服务器当唯一代码源。
- 使用语义化版本，例如 `1.0.10`。
- 每次发布生成变更日志、依赖清单和产物 SHA256。
- 数据库迁移、后端镜像、桌面安装包、桥接包版本相互兼容。

### 5.3 持续集成

每次提交自动执行：

1. Python 和 JavaScript 语法检查。
2. 单元测试。
3. 多租户和权限测试。
4. 数据库迁移升级和降级测试。
5. 前端构建。
6. 桌面端构建。
7. 许可证和依赖漏洞扫描。
8. 部署包完整性校验。

### 5.4 发布流程

开发环境 -> 测试环境 -> 灰度租户 -> 全量发布。

数据库迁移使用扩展、迁移、收缩三段式：

1. 先增加兼容字段和索引。
2. 双写或后台回填。
3. 验证通过后再删除旧字段。

### 5.5 桌面端升级

- 安装包使用代码签名证书。
- 发布包包含数字签名、版本号、兼容桥接版本和升级说明。
- 客户端启动时检查版本，但升级过程必须由用户确认。
- 新客户端和旧服务端、旧客户端和新服务端都要有兼容矩阵。
- 升级失败可以退回上一安装包。

### 5.6 回滚

- 保留上一版本应用文件和镜像。
- 发布前自动备份 PostgreSQL、Redis 关键状态和配置。
- 停机发布目标：回滚时间不超过 10 分钟。
- 数据库结构回滚遵循兼容策略，不做随意降级迁移。

### 5.7 验收标准

- 新环境可以一条命令完成部署。
- 发布失败不会让旧版本无法恢复。
- 数据库迁移失败时自动阻止应用启动。
- 安装包签名、哈希和版本一致。
- 灰度期间可以按租户关闭新功能。

## 六、测试体系

### 6.1 目标

测试覆盖安全性、稳定性、数据一致性、用户体验和部署恢复，不再只检查功能是否能运行。

### 6.2 测试分层

| 层级 | 重点 |
|---|---|
| 单元测试 | 权限、租户、状态机、幂等、分片、重试 |
| 接口测试 | API 契约、错误码、租户隔离、权限 |
| 数据库测试 | 唯一约束、迁移、回填、并发锁 |
| 前端测试 | 登录、角色菜单、状态展示、错误处理 |
| 桥接测试 | 读取、去重、领取、发送、回执、恢复 |
| 端到端测试 | 客户消息到最终回复的完整链路 |
| 压测 | API、队列、数据库、WebSocket、并发发送 |
| 混沌测试 | Redis 重启、数据库短暂不可用、微信关闭、电脑重启 |
| 安全测试 | 越权、注入、密钥泄露、文件上传、支付回调 |
| 灾备测试 | 备份恢复、回滚、历史数据校验 |

### 6.3 多租户测试矩阵

至少使用三个租户：

- 租户 A：普通企业。
- 租户 B：拥有同名客户、同名文件、相同订单编号。
- 租户 C：被停用或试用到期。

测试客户、订单、知识库、导出、删除、桥接回执、WebSocket 和后台任务全部不能串租户。

### 6.4 核心验收指标

- 跨租户数据泄漏：0。
- 未经授权的写操作：0。
- 重复发送：0，最终不确定任务必须进入人工复核。
- 消息接收后任务丢失：0。
- 服务重启后恢复率：100%。
- 普通接口 P95 延迟小于 500 毫秒。
- 不包含模型生成的核心 API P95 延迟小于 1 秒。
- 发送成功率在受控渠道达到 99% 以上。
- 回滚演练成功率：100%。

### 6.5 测试数据

- 使用脱敏、可重复生成的多租户测试数据。
- 禁止在测试环境复制真实客户数据库。
- 每条核心测试用例记录租户、角色、输入、期望结果和审计结果。

## 七、合规与隐私

### 7.1 目标

建立客户数据全生命周期管理，覆盖采集、存储、使用、共享、导出、删除和审计。

### 7.2 数据分类

| 级别 | 数据 | 要求 |
|---|---|---|
| 高敏感 | 微信聊天、手机号、支付、身份 | 加密、最小权限、严格审计 |
| 中敏感 | 客户画像、订单、线索 | 租户隔离、访问控制 |
| 低敏感 | 配置、公开知识 | 常规访问控制 |
| 密钥类 | API Key、数据库密码、模型密钥 | KMS 或密钥管理，永不写日志 |

### 7.3 隐私控制

- 明示采集目的和使用范围。
- 客户拒绝后停止营销触达。
- 日志默认脱敏手机号、邮箱、微信 ID 和模型密钥。
- 本地解密的微信数据库增加加密存储和到期清理。
- 发送失败截图不得上传到公网，诊断文件按天清理。
- 导出文件加水印、下载审计和有效期。
- 备份也执行保留期限，不能让删除数据永久留在备份中。

### 7.4 数据主体权利

1. 查询授权和数据用途。
2. 更正客户资料。
3. 导出客户数据。
4. 撤回授权。
5. 删除客户数据。
6. 提供删除结果和审计编号。

### 7.5 删除流程

- 建立统一删除编排，覆盖 PostgreSQL、Redis、对象存储、向量库、本地桥接和备份策略。
- 删除任务必须可重试、可查看进度和可审计。
- 删除失败不能返回成功。
- 对备份中的历史数据使用过期淘汰，不直接篡改历史备份。

### 7.6 合规文档

- 隐私政策。
- 用户授权说明。
- 数据处理协议。
- 第三方模型和数据供应商清单。
- 安全事件响应流程。
- 数据泄露通知流程。
- 个人信息请求处理流程。
- 内部权限和访问审批制度。

### 7.7 验收标准

- 删除申请在约定时间内完成，并输出删除证明。
- 普通日志中不存在手机号、邮箱、完整微信 ID 和密钥。
- 导出、删除、授权、转人工操作全部可审计。
- 个人微信桥接的使用范围、留存和清理规则明确。

## 八、实施顺序

### 第一阶段：安全边界

周期：2 到 3 周。

- 完成租户数据盘点和数据库迁移设计。
- 完成 RBAC、数据范围和 API Key 改造设计。
- 修复支付回调、默认密码和超管权限。
- 建立多租户和权限自动化测试。

### 第二阶段：知识库和合规

周期：3 到 4 周。

- 迁移到 PostgreSQL + pgvector。
- 建立文档、切片、向量和索引版本模型。
- 建立知识审批、引用、评测和回滚。
- 建立数据分类、脱敏、导出和删除流程。

### 第三阶段：发布和测试

周期：2 到 3 周。

- 建立 Git、CI、版本产物和部署清单。
- 完成安装包签名和版本兼容检查。
- 建立端到端、压测、混沌和灾备测试。
- 完成灰度发布和回滚演练。

### 第四阶段：灰度上线

周期：2 周。

- 选择一个非关键租户灰度。
- 每天检查跨租户、权限、知识检索、发送成功率和人工复核。
- 无严重问题后再开放到第二批和全量租户。

按当前一人开发和 AI 辅助的节奏，整体合理周期为 8 到 12 周。若多人并行且第一阶段与知识库设计并行，可压缩到 6 到 8 周。

---

## 九、最终商用验收门槛

只有同时满足以下条件，才进入正式商用：

- 跨租户访问测试全部通过。
- 普通用户无法访问管理员和财务接口。
- API Key 可以吊销、轮换和限制权限。
- 知识检索只读取当前租户已审批文档。
- 每个回复都能记录知识来源或明确无知识依据。
- 发布、回滚和数据库迁移都有自动化脚本。
- 安装包已签名且版本可追踪。
- 断电、断网、Redis 重启和微信关闭场景可恢复。
- 删除、导出和敏感操作可审计。
- 真实灰度租户连续运行 14 天无数据安全问题。
