# P0 最终优化清单

> 目标：把销售智能体从“页面能打开”整理成“内部商用闭环可运行”。
> 原则：只做必须闭环，不做新增伪模块；所有改动先备份，能验证再交付。

---

## 1. P0 总目标

完成以下 8 个闭环后，P0 才算通过：

1. 数据真实进入服务器。
2. 所有渠道统一进入会话中心。
3. 企业微信与微信客服可配置、可查看、可测试。
4. 系统管理只有管理员可见且接口有权限保护。
5. 消息不重复、上下文不乱、发送有审计。
6. 桌面端与网页端使用同一套前端逻辑。
7. 前端没有空白模块、英文残留、JSON/代码裸露。
8. 有可重复执行的部署、同步、回滚和验收方式。

---

## 2. P0 任务清单

### P0-01 服务器同步与历史数据迁移

**目标**

把本地中台前端和历史数据同步到服务器，并把 SQLite 数据迁移到 PostgreSQL。

**范围**

- 上传同步包到 `/opt/sales-agent/sync-20260908`。
- 执行 `sync_ui_data_20260908.sh`。
- 备份当前 `.env`、`data`、`vector_store`。
- 同步 `console.html`、`solda.js`、`solda-enterprise.js`、`vision_console.html`。
- 同步 `customers.db`、`metrics.db`、`llm_usage.db`、`vector_index.json`。
- 同步知识库、上传文件、对象存储、通知、审计、向量库。
- 重建容器。
- 执行 SQLite 到 PostgreSQL 迁移。
- 重建知识库索引。

**验收标准**

- `/health` 返回 200。
- 控制台能打开，侧边栏为新的分层结构。
- 客户、线索、订单等页面能显示历史数据。
- 服务器旧数据有备份。

---

### P0-02 企业微信与微信客服接入页面

**目标**

当前后端已有企业微信和微信客服能力，但前端侧边栏没有入口。P0 必须把这两个通道接回中台。

**范围**

- 侧边栏“渠道接入”下增加：
  - 企业微信
  - 微信客服
- 复用后端接口：
  - `GET /api/v1/wecom/status`
  - `POST /api/v1/wecom/test-send`
  - `GET /api/v1/channels/overview`
- 页面展示：
  - 企业微信是否已配置
  - 企业 ID 脱敏
  - Agent ID
  - 微信客服是否已配置
  - 微信客服 OpenKfId
  - 回调地址
  - 最近状态或错误
  - 测试发送入口
- 测试发送仅管理员可用，并写审计。

**验收标准**

- 管理员能看到企业微信与微信客服入口。
- 页面不显示完整 Secret。
- 未配置时显示明确状态和指引。
- 测试发送成功后页面有成功提示。

---

### P0-03 统一会话中心

**目标**

把所有渠道的客户消息集中到一个页面，而不是散落在各渠道页面中。

**范围**

- 新增“会话与智能体”导航组。
- 会话中心首页展示：
  - 会话列表：渠道、客户、昵称、状态、最近消息时间
  - 会话筛选：渠道、状态、关键词
  - 会话详情：最近消息、客户身份、转人工状态
- 优先复用后端接口：
  - `GET /api/v1/commercial/channel/sessions`
  - `GET /api/v1/commercial/channel/sessions/{id}/messages`
  - `POST /api/v1/commercial/channel/sessions/{id}/assign`
  - `POST /api/v1/commercial/channel/sessions/{id}/close`
- 如果数据模型仍不完整，先补服务端统一会话模型，而不是在前端临时拼数据。

**验收标准**

- 企业微信、微信客服、公众号、网页客服、个人微信的消息都能在会话中心看到。
- 普通成员只能看到自己权限范围内的会话。
- 会话关闭、转派、查看详情都有审计记录。

---

### P0-04 消息中枢监控页

**目标**

让“统一消息中枢”不再只存在于代码里，也要能在中台被观察。

**范围**

- 新增“消息中枢”或“运行状态”页面。
- 展示：
  - 今日接收消息数
  - 今日去重数量
  - 今日发送成功数
  - 今日失败数
  - 队列积压
  - 当前 Worker 状态
  - 最近失败原因
- 支持管理员手动测试：
  - 消息幂等
  - 回复发送
  - 队列状态
- 失败率达到阈值时产生告警。

**验收标准**

- 页面数据不是写死的空数组。
- 同一消息重复推送时能看到去重结果。
- 发送失败原因能定位到渠道或 AI 错误。

---

### P0-05 系统管理权限闭环

**目标**

系统管理不能只靠前端隐藏，必须有后端权限兜底。

**范围**

- 前端：
  - 系统管理菜单仅管理员显示。
  - 普通成员直接进入系统管理 URL 时显示无权限。
- 后端：
  - 系统管理相关接口统一加 `require_admin`。
  - 对当前已有接口逐项检查：
    - 用户管理
    - 角色权限
    - 企业设置
    - 备份恢复
    - 审计日志
    - 合规设置
- 系统管理内的新增、编辑、删除、导出、恢复全部写审计。

**验收标准**

- 普通角色看不到系统管理入口。
- 普通角色绕过前端调用系统管理 API 返回 403。
- 管理员操作后审计日志可查询。

---

### P0-06 前端数据质量与中文化

**目标**

清理“页面有入口但没数据、显示代码、显示英文”的问题。

**范围**

- 每个 P0 页面检查：
  - 是否有真实数据加载
  - 是否有空状态
  - 是否有错误提示
  - 是否出现英文模块名
  - 是否直接输出 JSON
  - 按钮和表单是否与后端字段一致
- 重点页面：
  - 数据总览
  - 客户档案
  - 线索管理
  - 商机管理
  - 订单售后
  - 报价合同
  - 回款交付
  - 会话中心
  - 渠道接入
  - 系统管理

**验收标准**

- 页面无英文残留。
- 页面无原始 JSON。
- 数据为空时显示中文空状态。
- 数据加载失败时显示可理解错误。

---

### P0-07 桌面端前端收敛

**目标**

桌面端不再维护一套与网页端不一致的页面。

**范围**

- 桌面端继续使用 `renderer/index.html` 作为唯一中台入口。
- 视觉执行器不再以 iframe 页面为主，改为中台内的一个模块。
- `desktop-client/web/console.html` 不再作为正式中台入口，避免双份维护。
- 桌面端与网页端共用同一套侧边栏分组和权限逻辑。
- 重新构建 Windows `.exe` 并做一次安装测试。

**验收标准**

- 桌面端登录后看到的导航与网页端一致。
- 普通账号看不到系统管理。
- 视觉执行器开关、状态、审计可在客户端内操作。
- 客户端退出后视觉执行器停止。

---

### P0-08 P0 验收脚本

**目标**

所有 P0 改动都要有自动化或半自动验收。

**范围**

- 在 `deploy/` 下补充：
  - 前端可访问性检查
  - 登录与权限检查
  - 渠道配置状态检查
  - 会话中心数据检查
  - 数据迁移结果检查
  - 系统管理 403 检查
- 本地保存验证脚本，服务器部署后执行。

**验收标准**

- 每个 P0 项至少有一条可重复验证用例。
- 验证结果可以明确区分“通过 / 失败”。

## 3. P0 明确不做

以下内容不属于 P0，避免再次把范围做散：

- 不做官网。
- 不做支付牌照或自建支付。
- 不做完整 CDP。
- 不做可视化工作流编排器。
- 不做商城、拼团、分销。
- 不做白标和私有化。
- 不做公开 API 市场。
- 不做没有真实数据来源的报表页面。

---

## 4. P0 完成定义

P0 只有在以下所有条件同时满足时才算完成：

1. 服务器已同步并正常运行。
2. 历史数据迁移完成且页面可查询。
3. 企业微信、微信客服、公众号、个人微信、网页客服都进入统一会话中心。
4. 同用户消息不重复回复。
5. 转人工后可停止自动回复并通知负责人。
6. 系统管理前端不可见、后端不可越权。
7. 桌面端与网页端导航一致。
8. 所有 P0 页面无英文残留、无代码裸露、无空白模块。
9. 部署、同步、回滚、验收都有文档和脚本。
10. 核心链路至少完成一次真实端到端测试。
