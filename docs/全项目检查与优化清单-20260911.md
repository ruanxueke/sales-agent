## 0. 结论速览

项目功能面很宽（60+ 路由、80+ core 模块），代码里能看到不少正确的工程直觉
（HTTP 幂等、`skip_locked` 认领、双层去重、慢查询日志、`commercial.py` 的租户条件写得很规范）。

但**当前状态不能直接按"企业级可商用、多用户直连"上线**，原因集中在三类：

1. **数据源分裂** —— 生产用 PostgreSQL，但有 21 个模块绕过 ORM 直连 SQLite 旧库，迁移链路也没接进部署流程。
2. **多租户在最关键的那条链路上失效** —— 本机桥接用 API Key 鉴权，而 API Key 身份拿到的租户是 `None`，等于关掉了租户过滤。
3. **若干"静默失败"** —— 乱码话术、Celery 重试死代码、公众号任务入错队列，都是不报错但客户侧直接出问题。

按严重度分四档：**A 阻断级 6 项 / B 高危安全 8 项 / C 稳定性与正确性 16 项 / D 优化建议（分三阶段）**。

## A. 阻断级问题（会导致线上事故 / 数据错乱 / 客户可见故障）

### A2. 多租户在「个人微信接待链路」上完全失效（对应"多用户直连不出问题"的核心诉求）

链路：`core/security.py: current_tenant()` → token 身份返回用户 tenant_id；**API Key 身份返回 `None`**。
本机桥接（`wechat_bridge/`）用的是 `PERSONAL_WECHAT_API_KEY`，**属于 API Key 身份**，于是：

| 接口 | 代码位置 | `tenant_id=None` 的实际后果 |
|---|---|---|
| `GET /api/v1/personal-wechat/tasks`（认领任务） | `api/personal_wechat.py:95-100` → `core/personal_wechat.py: claim_tasks` | 租户条件被 `if tenant_id is not None` 跳过 → **跨租户认领**：只要是同一个 `account_id`，A 租户的桥接会领走 B 租户的回复任务 |
| `POST /tasks/{id}/ack` | `api/personal_wechat.py:110-116` → `ack_task` | 无租户校验，任意桥接可改写任意任务状态 |
| `POST /events` | `core/personal_wechat.py: ingest_event` | `tid = tenant_id if not None else payload["tenant_id"] or 0` → **租户号由请求体自报**，客户端说自己是几号租户就是几号 |
| `POST /bridge/heartbeat` | `heartbeat()` | `BridgeHeartbeat` 模型里**根本没有 `tenant_id` 字段** → 永远回退到 `tid = 0` |
| `POST /bridge/settings` + `GET /bridge/settings` | `update_settings()` / `get_settings()` | 同上，**只能作用在 tenant 0** |
| `GET /status` | `status()` | 无租户过滤，取 `last_seen` 最新的一行 → 可能显示别的租户的实例 |

**最直接的业务后果**：控制台（token 身份，如 tenant_id=2）点「开始识别」，写的是 tenant 2 的 `recognition_enabled`；
而桥接（API Key 身份）心跳读写的永远是 tenant 0 → **开关到不了桥接**，界面就表现为"已连接但待识别"。
这与之前排查到的现象是同一类根因，只是当时掩盖在实例碰撞问题之下；只要接入第二个租户就会必然复现。

- **优化（二选一，建议前者）**：
  1. **凭据即租户**：给每个租户签发独立 API Key，在 `core/security.py` 建立 `key → tenant_id` 映射，`current_tenant()` 对 API Key 也返回真实租户，彻底去掉"API Key = 无视租户"的规则；
  2. **显式声明 + 校验**：`BridgeHeartbeat` / `BridgeSettings` 增加 `tenant_id` 字段，并在服务端校验"该 Key 是否有权操作该租户"，不匹配直接 403（而不是静默落到 0）。
  另外：所有 `if tenant_id is not None` 的写法应改为"必须显式传入租户"，避免 `None` 退化成"看全部"。

### A3. Celery 重试分支是死代码 → 同用户并发消息被**静默丢弃**

- 文件：`core/tasks.py:179`
- 现状：`if not result.get("ok") and result.get("error") == "?????????"` —— 字面量是乱码占位符（连同第 176 行 docstring）。
- `core/reply_dispatcher.py:128` 实际返回的错误是 `"用户处理锁等待超时"` → 比较永远为 `False` → **不重试，任务直接返回**。
- 触发条件很常见：同一客户在 20 秒内连发两条消息（`LOCK_WAIT = 20.0`，`USER_LOCK_TTL = 120`），第二条拿不到锁 → `ok=False` → 被丢弃，**客户永远收不到第二条的回复**。
- **优化**：把"可重试错误"结构化，例如 `run_reply_task` 返回 `{"ok": False, "retryable": True, "error": "..."}`，任务侧按 `retryable` 判断 `self.retry()`；同时给所有 `retry` 加 `max_retries` 上限与指数退避，避免打爆。

### A4. `official` 容器入错 Redis 队列 → 公众号回复任务**永远不被消费**，且返回成功

- `docker-compose.yml`：
  - `api` / `worker` / `beat` 都设了 `CELERY_BROKER_URL: redis://redis:6379/1`
  - **`official` 服务只设了 `REDIS_URL: redis://redis:6379/0`，没有设 `CELERY_BROKER_URL`**
- `core/tasks.py:14` 回退逻辑：`broker = CELERY_BROKER_URL or REDIS_URL` → official 容器里的 Celery producer 落在 **db0**；而 `worker` 只监听 **db1**。
- 结果：`main.py --channel official` 收到的客户消息 → `enqueue_reply()` → `send_channel_reply_task.delay()` 写进 db0 → 无人消费。且 `enqueue_reply` 会返回 `{"ok": True, "queued": True}`，**没有任何报错**。
- 附带问题：`api` 容器没有 `CELERY_RESULT_BACKEND`（为 `None`），而 `worker` 写 results 到 db2，`task_track_started=True` 拿不到结果。
- **优化**：给 `official` 补齐 `CELERY_BROKER_URL` / `CELERY_RESULT_BACKEND`；把 `core/tasks.py` 的回退改成"环境变量缺失就显式报错/告警"，不要静默换库；`enqueue_reply` 增加 `ping` 校验后再返回 `queued`。

### A5. SQLite 与 PostgreSQL 双数据源并行（影响面最大）

- 生产：`docker-compose` 给 api/official/worker/beat 注入 `DATABASE_URL: postgresql://…@postgres:5432/sales`，ORM 走 PG。
- 但下列模块**绕过 ORM，直接用 `sqlite3.connect(data/customers.db)`**（实测 21 个文件）：

  | 层 | 模块 |
  |---|---|
  | core | `enterprise.py` `tenant.py` `billing.py` `analytics.py` `alerting.py` `audit.py` `monitor.py` `usage.py` `webchat.py` `feedback.py` `tools.py` `forecast.py` `citations.py` `compliance_flow.py` `knowledge_gaps.py` `llm_trace.py` `security_layers.py` `sales_crm.py` `tenant_migrate.py` |
  | api | `api/crm.py:101` `api/ticket.py:69` `api/prompt.py:21` `api/channels.py:155` `api/knowledge.py:40` `api/system_check.py:111` |
  | knowledge | `knowledge/knowledge_manager.py:94` |

- 后果（按严重度）：
  1. **读旧库**：`enterprise.performance()` / `leaderboard()` / `compute_commissions()` 执行
     `SELECT … FROM orders o LEFT JOIN leads l …`；`orders`/`leads` 是 ORM 表，**只存在于 PG**。宿主机上那份 `data/customers.db` 是上云前的遗物 —— 于是要么报 `no such table: orders`，要么**读到上云前的陈旧数据**，业绩榜/佣金**永远是老数字**。
  2. **表不在同一库**：`enterprise._init()` 建 `system_users`/`auth_tokens`/`sales_targets`/`commission_*`/`approval_rules`/`sla_policies`/`customer_tiers`；`tenant._init()` 建 `tenants`/`tenant_members`/`tenant_settings` —— **登录态、成员、配额全在 SQLite**，而业务数据在 PG。
  3. **`create_approval()` 写 `approval_flows`** —— 该表在 `core/models.py:345` 定义为 ORM 表（在 PG）。SQLite 侧从未建过 → 审批流创建直接失败。
  4. **多容器共享一个 SQLite 文件**：api/official/worker/beat 四个容器都挂载 `./data`，四个进程各自持连接并发写 → 高负载下 `database is locked`（代码里没有任何重试包装）。
  5. `tenant.check_quota()` 统计 SQLite 的 `customers` 表 → 生产恒为 `0` → **配额形同虚设**。
  6. `TenantManager._login_failures`、`EnterpriseManager._login_failures` 是**进程内存字典** → 2 个 uvicorn worker 可通过交替请求绕过"5 次失败锁 15 分钟"。

- **优化**：这是本次最需要下决心的一项。
  - 短期：明确"哪些是必须 PG 的"（登录/成员/配额/业绩/佣金/审批/SLA/审计/计费/工单/知识库），逐个迁到 ORM。
  - 若确实想保留本地 SQLite 作为轻量存储，则必须**与业务数据物理隔离到独立文件**（如 `data/ops.sqlite`），并在文档里写清"它不参与业务查询"，同时把并发写问题用单写者（worker 里串行）解决。
  - 登录失败计数、限流计数迁到 Redis（本来就该放那儿）。

### A6. 数据库迁移链路缺失 → 以后给已有表加字段会直接崩

- `migrations/versions/` 有 6 个 Alembic 版本（0001–0006）。
- 实测全仓库（排除 `release/`）**没有任何地方执行 `alembic upgrade`**：`docker-compose` 的 4 个服务用的是裸命令；没有 entrypoint 脚本；`Dockerfile` 也没有。
- 启动建表走的是 `core/db.py:init_db()` → `Base.metadata.create_all()`，它**只创建"缺失的表"，不会 ALTER 已存在的表**。
- 也就是说：一旦给现有表新增列（本项目历史上频繁发生，`PersonalWechat*` 这类新表就是靠 `create_all` 建出来的，但**加列不行**），生产库不会有这一列 → 运行时 `Unknown column` 崩。
- 顺带：`migrations/versions/` 里**没有 personal_wechat 相关表**（只到 0006），说明这一层已经和 ORM 定义脱节。
- **优化**：
  1. 部署流程接上 `alembic upgrade head`（entrypoint 或 compose `command` 前置）；
  2. 补齐从 0006 到当前 `models.py` 的迁移（至少包括 `personal_wechat_reply_tasks`、`personal_wechat_bridge_instances`、`channel_sessions`、`channel_messages` 等）；
  3. 把 `init_db()` 的 `create_all` 降级为"仅本地开发/测试"，生产以 alembic 为唯一权威；
  4. CI 增加"`models.py` 与迁移版本一致性"检查（`alembic check`）。

## B. 高危安全

### B1. `server.env`（含全部生产密钥）被打进镜像，且未进 gitignore

- `Dockerfile`：`COPY . .`
- `.dockerignore` 只排除了 `.env`，**没有排除 `server.env`** —— 而 `server.env` 里含
  `DEEPSEEK_API_KEY`、`DASHSCOPE_API_KEY`、`WECHAT_OFFICIAL_APP_SECRET`、`WECOM_*_SECRET`、`API_KEYS`、`ADMIN_API_KEYS` 等。
- `.gitignore` 只有 `data/`、`vector_store/`、`wechat_bridge/data/`、`*.pyc`、`__pycache__/` —— **`.env` 和 `server.env` 都没被忽略**。
- **优化**：`.dockerignore` 与 `.gitignore` 同时补上 `.env`、`server.env`、`*.env`；密钥只通过 compose `env_file` / 环境变量注入；立即轮换已进过镜像的所有密钥（镜像层里的密钥无法"删除"，只能换）。

### B2. 鉴权边界之外还有多个口子

`api_server.py:173-189` 的中间件只对 `path.startswith("/api/")` 生效。于是：

| 端点 | 问题 |
|---|---|
| `/health` | 公开；`core/db.py:check_db_health()` 在异常分支 `return {"database": str(e)}` —— SQLAlchemy 连接失败信息里**可能带完整 DSN（含口令）** |
| `/docs`、`/openapi.json` | FastAPI 默认开启 → 完整接口清单与参数结构对外公开 |
| `/ws/notifications` | **完全无鉴权**，任何人可连接 `core/realtime.hub` 接收实时通知广播 |
| `/static/*` | 公开（`console.html` 本身公开可接受，但它是"前端即凭证"的入口，见 B3） |

- **优化**：`/health` 只返回 `{"status":"ok"}`，详细指标移到需鉴权的 `/api/v1/aiops/health`；`FastAPI(docs_url=None, redoc_url=None, openapi_url=None)` 或给 docs 加鉴权；`/ws/notifications` 握手时校验 token，并在 `hub` 内按租户/用户过滤广播目标。

### B3. 控制台把「超管 API Key」存在 localStorage，且没有 CSP 兜底

- `static/console.html:1160` `const API_KEY = localStorage.getItem("sales_api_key")`，第 1221 行以 `X-API-Key` 发出，第 2008/2325 行写入。
- 该 Key 属于 API Key 身份 → `current_tenant()` 返回 `None` → **等价于跨租户超级权限**（这正是 A2 里那个规则的"设计用途"）。
- 同时 `security_headers_middleware` 只设了 `Content-Security-Policy: frame-ancestors 'self'`，**没有 `default-src` / `script-src`**，`X-XSS-Protection` 也已是废弃头。
- 也就是说：localStorage 里的超管 Key + 无脚本级 CSP = 一旦出现任何 XSS，攻击者拿走的是一个能读写**所有租户**数据的凭据。
  （本次核查了前端转义：`esc()` 实现完整（`& < > " '` 全转），127 处 `innerHTML` 中仅 7 处模板插值未走 `esc(` 且均为已转义/纯数值内容 —— 所以**目前没有找到可用的 XSS 入口**，但缺少深度防御。）
- 附带：API Key 无轮换、无过期、无 scope（`core/security.py` 里就是集合成员判断）。
- **优化**：控制台以 token 登录为主，API Key 只用于运维脚本；加 `default-src 'self'` 级 CSP；Key 支持轮换/过期/scope（只读/单租户）；localStorage 改 sessionStorage 或内存（配合 httpOnly Cookie 更好）。

### B4. 审计日志会写入原始 API Key

- `api_server.py:182-187`：鉴权失败时 `audit(actor=key or "anonymous", ...)` —— **把请求里带的密钥原样落库**（`core/audit.py` 落在 SQLite）。
- **优化**：只记 `key[:6] + "***"` 或哈希前 8 位；审计表加脱敏中间件。

### B5. 企业微信回调可被伪造，且合规记录已损坏

- `connectors/wecom.py:188-199`：`decrypt_message()` 内部 `except` 后 **`return body`（当明文解析）**。`handle_wecom` 只在 `"<Encrypt" in body` 时才尝试解密 → **攻击者直接 POST 明文 XML 即可注入任意"客户消息"**（签名从未真正强制校验）。`verify_signature()` 只在 GET 校验 URL 时用到。
- `connectors/wecom.py:262 / 264 / 266 / 281` 四处 `????`：
  - 262：`logger.error("??????????: %s", e)` → 同步失败原因不可读
  - 264/266：日志不可读
  - **281：`compliance_flow.add_consent(external_userid, source="wecom_kf", content="??????")`** → **合规授权同意的记录内容本身是乱码**，这是合规证据链问题，不只是日志。
- **优化**：回调强制验签，`decrypt_message` 失败直接返回 4xx，**删除明文兜底**；修这 4 处乱码；对 `wecom_kf` 只处理 `msgtype=="text"` 的做法补上"非文本消息记入会话但不自动回复"的显式分支（现在是静默丢弃）。

### B6. Redis 无密码 + 危险端口映射到宿主 + 淘汰策略会吃掉锁和去重键

- `docker-compose.yml:27` `redis-server --maxmemory 128mb --maxmemory-policy allkeys-lru`，**没有 `requirepass`**。
- `postgres`(5432) / `redis`(6379) / `api`(5010) / `official`(8080) 全部 `ports:` 映射到宿主。实测 `<your-server-ip>` 外部 5432/6379/5010/8080 **均关闭**（靠云安全组兜住），但一旦换机器、加机器或安全组被改，就是裸奔。
- **最容易被忽视的一条**：db0/db1/db2 同时承载 **Celery broker、用户处理锁（`reply:lock:*`）、消息去重键（`reply:done:*`）、限流计数、语义缓存**，而策略是 `allkeys-lru` + 128MB。内存一紧，**锁会被淘汰**（串行保护失效）、**去重键会被淘汰**（→ 同一客户收到重复回复）、**限流计数会被淘汰**（→ 限流失效）。这是商用场景下最容易被投诉的表现。
- 另：只配了 RDB 快照（有 volume 无 `appendonly`）→ 重启可能丢锁/去重键。
- **优化**：Redis 加密码并只监听内网；删掉 postgres/redis 的宿主端口映射；把"必须持久、不能被淘汰"的键（锁/去重/限流）与"可淘汰"的缓存拆成两个实例或改用 `volatile-lru` + 对关键键不设 TTL/单独 DB；开 AOF。

### B7. 口令存储与登录锁定不达商用标准

`core/enterprise.py`：
- `_hash(password, salt)` = `sha256(username + password)` —— 无 KDF、无迭代、盐就是用户名（可预计算）；`hashlib` 的极快哈希对撞库毫无抵抗力。
- `login()` 失败计数 `self._login_failures` 是**进程内字典** → 2 worker 交替打请求可绕过 5 次锁定；重启即清零。
- **优化**：改 `bcrypt` / `argon2`（`passlib` 或 `argon2-cffi`）；锁定计数放 Redis（`INCR` + `EXPIRE`）；登录接口加 IP 维度限流与验证码阈值。

### B8. 容器以 root 运行，且内存限制实际不生效

- `Dockerfile` 无 `USER` → 容器内 root；未设 `PYTHONUNBUFFERED=1`（`docker logs` 会延迟，排障困难）；无 `HEALTHCHECK`。
- `docker-compose` 的 `deploy.resources.limits` 在**普通 `docker compose up`（非 swarm）下被忽略** —— 那几行 `memory: 1024M / 2048M` 是装饰性的，workload 暴涨会直接吃光宿主。
- 默认 `CMD` 是 `python api_server.py & python main.py --channel official & wait`（与 compose 的 `command` 覆盖共存），容易误导后人。
- **优化**：加非 root `USER`、`PYTHONUNBUFFERED=1`、`HEALTHCHECK`；用 `mem_limit` / `deploy.resources` 二选一并写明前提（swarm）；删掉容易误解的默认 `CMD`。

## C. 稳定性与正确性

### C1. 异常被大面积静默吞掉
`except Exception: pass` 计数（core）：`platform.py` 12、`portrait.py` 6、`aiops.py` 5、`followup.py` 4、`agent.py` 3、`compliance_flow.py` 3，其余 1–2 若干。
叠加 `core/tasks.py:51 _safe` 装饰器把异常吃掉并 `return None` → **Celery 认为任务成功**（配合 `task_acks_late=True` 也不会重投）。
**优化**：至少改 `logger.exception`；`_safe` 改为"记录 + 返回结构化失败"，并让失败上报到 `alert_manager`；关键路径（发消息、落库、扣费）不允许静默。

### C2. `core/reply_dispatcher.py` 的三处逻辑缺陷
1. `make_msg_key()`：没有 `msg_id` 时用 `md5(channel:external_id:content)`，`MSG_DONE_TTL=86400` → **同一客户 24 小时内发同样的内容（"在吗""好的"）会被判定为重复而静默忽略**。
2. `_send_parts()`：分段发送时若第 2 段抛异常，前面已发出的部分不会回滚；任务整体重试 → **重复发送**（客户收到两遍）。
3. `_send_parts()` 对 `channel not in ("wecom_kf","wecom")` 只 `logger.warning` 并 `return 0` → **公众号 / 网页客服的回复根本没发出去**（而调用方拿到的是 `ok=True`）。
**优化**：无 `msg_id` 时改用"内容+短时间窗（如 30s）+ 客户端生成 id"策略；分段发送做逐段幂等记录，重试只补发未成功的段；为 `official`/`public_webchat` 补真实发送器，未接入的渠道让 `run_reply_task` 返回 `ok=False` 而不是假装成功。

### C3. LLM 路由状态是进程内的
`core/llm_router.py`：`_consecutive_failures`、`_failover_until`、`_force_model` 都是模块级实例变量。
- 2 个 uvicorn worker + 独立的 celery worker → 各自维护一套状态；
- 管理端"切换到备用模型"只作用于**处理该请求的那一个 worker**（另一台继续用主模型）；
- `record_failure()` 的 3 次连续失败在主/备之间也不共享。
**优化**：状态放 Redis（带 TTL 的 key），`get()` 时读取。

### C4. `enterprise.login()` 依赖模块导入顺序
`return {k: user[k] for k in ("id","username","name","role","tenant_id")}`，而 `system_users.tenant_id` 这一列**不是 `enterprise._init()` 建的**，是 `core/tenant.py:70` 用 `ALTER TABLE` 补的。
如果某条启动路径只导入了 `enterprise` 而没导入 `tenant`，`login()` 会 `KeyError`。
**优化**：`tenant_id` 写进 `enterprise._init()` 的建表语句（`CREATE TABLE IF NOT EXISTS` 之后再无条件 `ALTER ... ADD COLUMN IF NOT EXISTS`），去掉跨模块的隐式依赖。

### C5. `core/enterprise.py` 自身的设计问题
- 用自己的 SQLite `_init()` 建表，**无 `tenant_id` 维度** → 业绩/佣金/审批/SLA/客户分级全是"全局单租户"。
- `create_approval()` 写 `approval_flows`（ORM 表在 PG，SQLite 里不存在）→ 必失败。
- `check_approval_rules()` 只支持 `>` 和 `>=`；`condition_key` 用 `float(data.get(...) or 0)`，非数值条件会静默变 0。
- `compute_commissions()` 取 `rules[0]` 当唯一规则（`for order in paid` 里循环写 `rule = rules[0]`）→ 多规则配置形同虚设。
**优化**：整体迁到 ORM 并加 `tenant_id`；审批支持多运算符与操作符白名单；佣金规则按 `rule_type` + 优先级匹配。

### C6. `tenant.check_quota()` 在生产恒不生效
统计的是 SQLite 的 `customers` 表（见 A5）→ 永远 `used=0` → 配额检查永远通过。
**优化**：改统计 PG 的 `customers` / `customer_chat_log`（ORM 查询）。

### C7. `instance_id` 仍是全局唯一，与多租户天然冲突
`core/models.py` `PersonalWechatBridgeInstance.instance_id = Column(String(128), unique=True, nullable=False, index=True)`。
虽然应用层已改成按 `(instance_id, tenant_id)` 查并有跨租户占用拒绝（`_resolve_instance`），但**数据库约束仍是全局唯一** → 两个租户若使用相同默认实例号，插入时直接 `UniqueViolation`（表现为心跳 500，而不是那条友好的"已被其他租户占用"）。
**优化**：迁移为复合唯一 `UNIQUE(tenant_id, instance_id)`，或在 `instance_id` 生成时强制带租户前缀（服务端校验格式）。

### C8. 依赖管理不可复现
- `requirements.txt` 无锁文件，大量 `>=`；`langchain==1.3.14` 与 `langchain-community>=0.3.0`、`langchain-openai>=0.2.0` **未固定** → 存在解析冲突与"今天能装、明天装不上"的风险。
- `click==8.1.8` 与 `celery>=5.4.0` 的组合只靠注释说明，没有约束文件保护。
- `tests/test_concurrency.py` 需要 `fakeredis`，但 **`fakeredis` 不在 requirements.txt**。
**优化**：引入 `pip-tools` / `uv lock` / `poetry.lock` 生成哈希锁文件；CI 用锁文件安装；测试依赖单列 `requirements-dev.txt`。

### C9. 测试不可执行、无 CI
- `tests/` 是 9 个手写 `main() -> int` 脚本（不是 pytest/unittest 结构），**没有 runner**，`python -m pytest tests` 无意义。
- 本机实跑：`test_message_splitter` 通过（exit 0），其余 8 个因缺 `pydantic_settings` / `fakeredis` 报 `ModuleNotFoundError`（**属本机环境缺依赖，不是项目 bug**，但恰好说明没有环境清单与门禁）。
- **优化**：整理为 pytest 用例；补 `requirements-dev.txt`；CI 至少跑 import 检查（`python -c "import api_server"`）、乱码检查、迁移一致性检查、`message_splitter`/`personal_wechat`/`concurrency` 三组回归。

### C10. `release/`（25 个子目录 + 23 个 zip）没被 `.dockerignore` 排除
`COPY . .` 会把历史版本源码副本和压缩包打进镜像 → 构建变慢、镜像膨胀，且**历史版本里的旧密钥/旧配置随镜像一起分发**。
**优化**：`release/`、`*.zip`、`desktop-client/`、`docs/*.png` 加进 `.dockerignore`；产物统一放仓库外的 artifact 目录。

### C11. 配置项失效与双份词表
- `wechat_bridge/config.py` 解析了 `min_reply_delay` / `max_reply_delay` / `require_mention` / `reply_max_length`，**全项目无人使用**（"看起来配了，其实没生效"最容易误导运维）。
- `Dockerfile` 的 `ENABLE_SCHEDULER=true` 已无意义（定时任务已迁 Celery Beat）。
- **两套转人工词表不一致**：`core/agent.py` 硬编码 6 个（`转人工/人工客服/找人工/人工/客服电话/电话联系`）；`settings.WECOM_KF_HANDOVER_KEYWORDS = "人工,投诉,退款,转人工,转客服,客服处理,投诉处理"`（7 个，被 `reply_dispatcher` 和 `core/vision.py` 使用）。→ 走不同渠道时"转人工"的触发条件不同。
**优化**：删除死配置（或真正接线）；转人工词表收敛为单一配置源，按渠道可覆盖。

### C12. 提示词是"公众号版"，但被个人微信链路复用
`config/sales_prompt.txt`（236 行，编码正常）里明确写着：
- "你通过**微信公众号**与客户沟通"、"48 小时客服消息窗口"、"当前渠道是**公众号**"、"不要使用电话术语"

而 `core/agent.py` 的 `chat()` 对 `source="personal_wechat"` 等通路复用同一份提示词 → 个人微信/企微场景下话术带公众号语境，且"不要用电话术语"这类约束与企微场景冲突。
**优化**：提示词按渠道分文件（`sales_prompt.official.txt` / `.personal_wechat.txt` / `.wecom.txt`），`load_system_prompt(source)` 选择，公共部分抽成可拼装的片段。

### C13. 其他杂项（低危但应清）
- `connectors/wecom.py` 4 处 `????`（见 B5）。
- `fix_garbled_data.py` 里硬编码匹配 `????`（`106/108` 行）—— 它是为修乱码写的，但**只能匹配不能还原**，对 A1 无用。
- `core/models.py` 里 `MessageDedup.msg_id` 全局唯一（个人微信侧前缀已带 `tenant_id`，暂无冲突）。
- 无复合索引：`PersonalWechatReplyTask` 的认领查询按 `(account_id, status, lease_expires_at)` + 排序 `created_at, id`，目前是 4 个单列索引，小数据量没问题，量上来会走慢查询（好在已有 >500ms 慢查询日志）。
- `docker-compose` 日志无轮转（json-file 无 `max-size`）→ 长期运行会写满磁盘。
- 镜像未固定 `postgres:16-alpine` / `redis:7-alpine` 的具体补丁版本（次要）。
- 孤儿实例行 `desktop-wechat-auto`（tenant 0）待清（历史遗留，之前已记录）。
- `desktop-client` 把桥接作为子进程管理，**没有守护重启**：桥接进程异常退出后（历史上发生过崩溃循环）除非重启 Electron 否则不会自愈；`instance.json` 存在 `%APPDATA%`，多终端用户共用同一台机器时会共用同一 `instance_id`。
- `beat` 只支持启动时静态 `beat_schedule`，运行期改期需要重启。
